# Editor Visual de Flujos - v1.2 (Tablas, Pantalla en Runtime, Version-Agnostic)

> Version: v1.2
> Fecha: 2026-05-05
> Tipo: EVOLUTIVO
> App/Modulo: `flujos`, `legajos`, `frontend/flow-editor/`

---

## Descripcion

Tres mejoras conectadas que cierran el loop "configurar pantalla -> ver pantalla con datos reales":

1. **Editor de tabla simplificado** dentro de la solapa Interfaz: la tabla deja de competir con el modo avanzado, gana plantillas rapidas (chips de un click) y un acordeon estricto que reduce el ruido visual.
2. **Render server-side de pantalla declarativa v3 con interpolacion de variables**: las plantillas tipo `{{ ciudadano.dni }}` ahora se resuelven con datos reales tanto en la tarea del operador como en el panel del programa.
3. **Panel del programa version-agnostic**: el panel `programa_detail` y el header del editor del flujo cuentan instancias y muestran casos de cualquier version del flujo, no solo de la publicada hoy. Republicar deja de "perder" casos en curso.

## User Stories

```
Como configurador de programas quiero armar la tabla del paso "Derivacion" en pocos clicks
para mostrar al operador los datos del ciudadano sin tener que pensar en columnas o claves internas.
```

```
Como operador quiero ver, dentro del panel del programa, la pantalla del nodo con los datos
resueltos de cada caso parado en esa etapa, para entender de un vistazo quien esta esperando que.
```

```
Como configurador quiero republicar versiones del flujo sin perder de vista los casos en curso,
para iterar el diseno del flujo sin "esconder" inscripciones existentes detras de la version vieja.
```

## Criterios de aceptacion

### Editor de tabla
- [x] El selector "Tipo de bloque" tiene una sola entrada `Tabla` (no se separa simple/avanzado).
- [x] La tabla entra directo en modo simple: lista de filas etiqueta/valor.
- [x] El acceso al modo avanzado es un link discreto al pie ("Activar modo avanzado"), no un botón en igualdad jerarquica.
- [x] Hay 3 chips de plantillas rapidas que pre-cargan filas: Datos del ciudadano, Datos del programa, Estado del paso.
- [x] Existe chip neutro "Vaciar filas" cuando hay al menos una fila.
- [x] El resto de los bloques de la solapa Interfaz comparten el mismo modelo simple-first.

### Acordeon estricto
- [x] Solo una seccion expandida a la vez dentro de la solapa Interfaz.
- [x] Solo un bloque expandido a la vez dentro de la seccion abierta.
- [x] Al agregar una seccion nueva, se expande automaticamente y cierra cualquier otra.
- [x] Al agregar un bloque nuevo, se expande y cierra los demas.
- [x] Las tarjetas colapsadas muestran metadatos utiles ("Tabla simple - 3 filas", "Lista - 4 opciones", "Resumen - 5 items", etc.).
- [x] Las acciones de "Subir/Bajar/Duplicar" de seccion y bloque solo aparecen cuando esta expandido.
- [x] El boton "Cerrar todo" solo aparece cuando hay algo abierto.

### Render server-side de pantalla declarativa
- [x] El helper `flujos.infrastructure.ui_renderer.build_display_only_sections(ui_schema, instancia=None)` devuelve secciones listas para template, opcionalmente resueltas con datos del caso.
- [x] Solo procesa bloques de display (info, summary, table). Inputs editables se omiten en este renderer.
- [x] `_build_configured_resolution_schema` aplica la interpolacion sobre las `sections` cuando recibe una `tarea`. La pantalla del operador ve `40732138` en lugar de `{{ ciudadano.dni }}`.
- [x] El partial `legajos/programas/_pantalla_etapa.html` renderiza info/summary/table en Tailwind, con tonos por tipo de info, grids de summary y tablas responsive.

### Panel del programa muestra la pantalla del nodo
- [x] Cada tab de etapa, debajo de "Lectura operativa", muestra la seccion "Pantalla del nodo" si el nodo tiene bloques de display.
- [x] Si hay casos parados: tarjetas por caso con header (ciudadano, DNI, "Ingreso hace X") y la pantalla resuelta con sus datos reales.
- [x] Si no hay casos: mensaje + preview de la pantalla con placeholders literales.
- [x] Limite duro de 5 casos visibles por tab; los excedentes se anuncian con "Hay N casos mas".

### Version-agnostic
- [x] `_build_program_flow_context` filtra instancias y tareas por `version_flujo__flujo__programa=programa`, no por `version_flujo=version_publicada`.
- [x] El header del editor visual (`/flujos/programas/<id>/flujo/editar/`) cuenta instancias activas de cualquier version del flujo.
- [x] Republicar el flujo no resetea los contadores ni "esconde" casos en curso.
- [x] La estructura de etapas (lista de nodos visibles) sigue leyendose de la version publicada hoy: solo los conteos y casos son version-agnostic.

### Migraciones generadas

Ninguna nueva migracion. Sin embargo se hizo una **limpieza de schema drift** que fue necesaria para destrabar el flujo runtime:

- Drop de columnas huerfanas `iteracion_actual` (NOT NULL sin default - rompia INSERTs) y `resume_at` de la tabla `flujos_instanciaflujo`.
- Eliminacion de 3 entries fantasma en `django_migrations`: `flujos.0003_instanciaflujo_loop_fields`, `flujos.0004_node_audit_tables`, `flujos.0005_documentogenerado_archivo_blank`.

Estos artefactos venian de migraciones de otra rama que se aplicaron en local pero cuyos archivos `.py` ya no estan en el repo. El cleanup se hizo manualmente sobre la base de desarrollo del usuario; el codigo actual no las requiere. Tablas afectadas estaban en cero filas.

## Decisiones tecnicas

### 1. La tabla deja de ser "un campo mas" pero mantiene el schema de persistencia
- En el editor, la tabla se separa visualmente del flujo de configuracion de inputs. La UX entra simple-first, el modo avanzado es un escape hatch.
- El JSON guardado (`kind: 'table'`, `table_mode`, `columns`, `rows`, `empty_message`) **no cambia**. Mantiene compatibilidad total con tablas guardadas en versiones anteriores.

### 2. Render server-side declarativo en lugar de pasar el schema crudo al template
- `_pantalla_etapa.html` consume estructuras pre-procesadas (`display_kind`, `cells`, etc.). El helper `build_display_only_sections` hace el trabajo de aplanar el schema y resolver variables.
- Asi el template puede ser simple, declarativo, sin lógica de filtrado de tipos. Es el mismo patron que ya usaba `forms.py:_build_display_item` para la tarea del operador.
- **Razon adicional**: forzar interpolacion server-side evita filtrar `{{ ciudadano.dni }}` literal a HTML, eliminando tambien el riesgo de XSS por contenido editable mal-escapado.

### 3. Panel version-agnostic para casos vivos, version-publicada para estructura
- Republicar archiva la version anterior pero las instancias siguen vivas en esa version vieja. El panel debe mostrar el trabajo real, no solo lo que nacio en la version publicada hoy.
- La **estructura visible** (etapas, transiciones, ui_schema) sigue leyendose de la version publicada actual: representa el "mapa" del flujo segun el diseño vigente.
- Los **casos vivos** se traen de cualquier version: muestran el trabajo en curso.
- **Edge case identificado**: si una instancia esta parada en un nodo que ya no existe en la version publicada actual, no aparece en el panel. Se acepta como deuda tecnica - no es comun y no impide operar las instancias desde la bandeja directa.

### 4. Acordeon estricto en lugar de master-detail
- Se eligio el cambio mas barato (acordeon mutex) por sobre rediseñar el modal completo.
- Si la densidad sigue siendo alta despues de probar con usuarios reales, el siguiente paso es master-detail (lista de bloques a la izquierda, editor a la derecha).
- Razon: cambio reversible, schema sin tocar, alta probabilidad de cubrir el problema sin invertir tiempo en restructuracion completa.

### 5. Plantillas rapidas con variables verificadas en runtime
- Las 3 plantillas (`Datos del ciudadano`, `Datos del programa`, `Estado del paso`) usan solo variables que ya circulan en el codebase: `ciudadano.dni`, `ciudadano.nombre_completo`, `ciudadano.email`, `programa.codigo`, `programa.nombre`, `usuario.nombre_completo`.
- No se proponen variables "supuestas" que podrian no existir; menos friccion al usar las plantillas.

## Limitaciones conocidas / deuda tecnica

### Funcional
- **Filas duplicadas en la tabla**: si el operador aprieta varios chips de plantilla en la misma tabla sin "Vaciar filas", las filas se acumulan. Es comportamiento "append-only" intencional para no destruir trabajo, pero genera duplicados visibles. Mitigacion: el chip "Vaciar filas" esta a la vista cuando hay datos.
- **No hay autocompletar de variables** en el campo `Valor` de cada fila. Configurar `{{ ... }}` aun requiere conocer la estructura del contexto. Plan: dropdown de variables disponibles inferidas del runtime context (proximo evolutivo).
- **No se reordenan filas con drag-and-drop**. Solo se eliminan/agregan al final.

### Pantalla en programa_detail
- **Sin link a la tarea individual** desde la tarjeta de cada caso. El operador ve quien esta parado pero tiene que ir manualmente a la bandeja para resolver. Plan inmediato: agregar boton `Abrir tarea` en cada tarjeta que lleve a `/flujos/tareas/<id>/`.
- **Limite duro de 5 casos por tab**. No hay paginacion. Para programas con muchos casos en la misma etapa, el operador ve "Hay N casos mas" pero no puede expandir esa lista.
- **Instancias en nodos eliminados** quedan invisibles en el panel. No es un problema activo (el flujo del usuario no borra nodos), pero podria serlo en flujos refactorizados.

### Version-agnostic
- **Las instancias viejas no ven cambios de UI nuevos**. Si un caso arranca en v10 y el configurador agrega un campo radio en v14, el operador que abra esa tarea sigue viendo la pantalla de v10. Es **correcto** desde la perspectiva de auditoria (cada caso ejecuta la version donde nacio), pero confuso si el configurador espera que "todo el sistema use el ultimo diseño". No hay plan de migracion automatica.

### Schema drift en bases de desarrollo
- El cleanup de columnas huerfanas y migrations fantasma fue manual. Si otros desarrolladores tienen el mismo drift, deberan repetir el procedimiento. Documentar en `docs/team/entorno-local.md` un script idempotente seria util.

## Como funciona end-to-end

```
[Editor React]
    1. Configurador abre nodo Derivacion -> solapa Interfaz
    2. Click "Agregar tabla de datos"
    3. Click chip "+ Datos del ciudadano" -> filas pre-cargadas con {{ ciudadano.dni }} etc.
    4. Click "Publicar v14"
        |
        v JSON guardado en VersionFlujo.definicion
[Backend - inscripcion]
    5. Se crea InscripcionPrograma
    6. Signal `iniciar_flujo_inscripcion` -> FlowRuntime.iniciar()
    7. Crea InstanciaFlujo en v14, nodo_actual = primer nodo
    8. Si nodo_actual es accion_humana -> crea TareaFlujo PENDIENTE
        |
        v Datos persistidos
[Operador abre la tarea]
    9. URL `/flujos/tareas/<id>/`
    10. selectors._build_configured_resolution_schema:
        - Lee ui_schema de la version_flujo de la instancia
        - Llama a build_flow_template_context(instancia) -> {ciudadano: {dni: '36397539', ...}, programa: {...}}
        - Llama a render_flow_template_value(sections, context) -> reemplaza {{ ... }} con valores reales
        - Devuelve resolution_schema con sections resueltas
    11. forms._build_display_item construye estructura para template
    12. tarea_detalle.html renderiza la tabla con DNI=36397539
        |
        v Operador completa decision
[Resolver]
    13. POST a /flujos/tareas/<id>/resolver/ con { aprobado: 'true' }
    14. Runtime evalua transiciones desde el nodo
    15. Avanza al nodo siguiente segun condicion
[Panel del programa - paralelo]
    16. URL `/legajos/programas/6/`
    17. _build_program_flow_context:
        - Lee version publicada -> arma estructura de etapas (mapa visible)
        - Filtra InstanciaFlujo por version_flujo__flujo__programa (todas las versiones)
        - Para cada caso parado en cada etapa: build_display_only_sections(ui_schema, instancia=inst)
        - Los placeholders se resuelven igual que en la tarea
    18. programa_detail.html itera stages y renderiza pantalla del nodo con datos reales
        - Tarjeta por caso con header del ciudadano + tabla resuelta
```

## Como probar manualmente

1. **Editor**: abrir `/flujos/programas/6/flujo/editar/` -> nodo Derivacion -> solapa Interfaz. Verificar que solo una seccion este expandida y que las tarjetas colapsadas muestran metadata util.
2. **Tabla**: agregar bloque `Tabla`. Click chip "+ Datos del ciudadano" -> 3 filas precargadas. Click chip "Vaciar filas" -> tabla queda vacia.
3. **Publicar**: cambiar algo y publicar nueva version.
4. **Inscripcion**: inscribir un ciudadano nuevo al programa. Verificar que se crea InstanciaFlujo en la version recien publicada con TareaFlujo PENDIENTE.
5. **Pantalla del operador**: abrir `/flujos/tareas/<id>/`. La tabla debe mostrar DNI, nombre, etc. del ciudadano (no `{{ ... }}` literal).
6. **Panel del programa**: abrir `/legajos/programas/<id>/`. Tab de la etapa donde esta el caso. Debe verse seccion "Pantalla del nodo" con tarjeta del caso y tabla resuelta.
7. **Republicar**: volver al editor, cambiar algo, publicar otra version. El panel del programa **debe seguir mostrando los casos en curso**, sin volver a 0.
