# Motor de Flujos - v1.1

> Version: v1.1
> Fecha: 2026-05-01
> Tipo: EVOLUTIVO
> App/Modulo: `flujos`

---

## Descripcion

El motor de flujos deja de ser solo un runtime backend y suma operatoria humana usable en backoffice. Los nodos `accion_humana` ahora generan tareas reales, con bandeja, detalle, asignacion, reasignacion, resolucion web/API y un contrato explicito de formulario por nodo. Esto permite operar un caso sin editar JSON manualmente y deja mejor alineados runtime, UI y futuras integraciones.

## User Story

```
Como operador del backoffice quiero operar pasos humanos del flujo desde una bandeja con formularios tipados
para resolver tareas reales del programa sin editar JSON manualmente y con trazabilidad completa
```

## Criterios de aceptacion

- [x] Los nodos `accion_humana` materializan una `TareaFlujo` pendiente al entrar en ese paso
- [x] Al avanzar o cancelar la instancia, las tareas pendientes relacionadas se resuelven o cancelan automaticamente
- [x] Existe bandeja web de tareas con filtros por programa, asignado y estado
- [x] Existe detalle web de tarea con contexto acumulado, historial y formulario de resolucion
- [x] Se puede asignar y reasignar una tarea pendiente desde bandeja o detalle
- [x] La asignacion y reasignacion generan trazabilidad en `InstanciaLog`
- [x] Existen endpoints JSON para listar, ver, asignar y resolver tareas
- [x] El contrato `config.formulario` se valida al guardar/publicar y tiene prioridad sobre heuristicas
- [x] Los formularios tipados soportados hoy son `boolean_decision`, `text_input` y `choice_select`
- [x] Las tareas con input tipado dejan de aparecer como resolubles directas desde la bandeja

## Decisiones tecnicas

- **`TareaFlujo` como pieza operativa minima:** en vez de agregar una entidad paralela por tipo de paso, los nodos `accion_humana` materializan una tarea reutilizable y auditable.
- **`config.formulario` como contrato unico:** el formulario del paso humano deja de inferirse solo desde transiciones y pasa a declararse explicitamente en el nodo, manteniendo heuristica solo como fallback de compatibilidad.
- **Misma logica para web y API:** la bandeja HTML y la API JSON comparten selectors y schema de resolucion para no divergir entre superficies.
- **Publicacion mas estricta:** la validacion del contrato tipado corre en modo `publish`, evitando publicar definiciones que luego el runtime no pueda operar.

## Limitaciones conocidas / deuda tecnica

- Todavia no hay enforcement completo de roles por paso dentro del contrato del flujo.
- Los tipos de formulario tipado siguen limitados a tres casos comunes; numericos, fechas o formularios compuestos quedan para una version futura.
- No existe aun smoke test automatizado de round-trip completo editor -> guardar -> publicar -> recargar.
- Las tareas territoriales moviles siguen como linea futura; esta version cubre operatoria humana de backoffice.

## Cambios respecto a version anterior

La v1.0 dejaba listo el motor, las versiones y la API basica de definicion/publicacion, pero los pasos humanos todavia no eran operables. La v1.1 agrega la superficie operativa completa del runtime humano: tareas materializadas, bandeja, detalle, API de operatoria, auditoria de responsable y formularios tipados declarados por nodo.
